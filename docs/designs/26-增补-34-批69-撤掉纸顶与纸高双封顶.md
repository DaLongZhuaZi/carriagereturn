# 26-增补-34-批69-撤掉纸顶与纸高双封顶（纸一直向上出屏）

## 0. 背景与判定

- 批 68 桌面端推回 `9ca0eab`（2026-11-21 22:14）：纸底钉死（内层 Column 改确定高 `paperAreaH()`）、纸可拖动、`paperUserOffsetVp` 250ms 回位、换纸动画改在渲染出的纸上做 translate。自检称纸底恒等式（`paperTop＋paperBox＝405.2`）与 dump（纸底 897px）都对，滑动钳制（`max＝paperGrowVp−paperAreaH＝60.4`）与换纸时序（600ms）也对。
- 用户 2026-11-21 22:18 在最新提交上指出只剩一个问题：**纸占满上半部分的高度后，并没有继续往上超出屏幕边缘，而是转为向下延伸**。这是错的。
- 沙箱确认：这不是批 68 的锚定没做住（纸底确实钉在视口底），而是 `recalcPaperHeight()` 里**纸顶与纸高各有一道封顶**，两道合起来把纸向上的路堵死了。

## 1. 根因（读码，`9ca0eab` 的 `Index.ets`／`recalcPaperHeight()`）

### 1.1 第一道：纸顶下限 `capTop`——纸顶到了就不再上移

```ts
this.paperTopTargetVp = this.carriageTopVp - paperBandBase
  - this.docModel.getCursor().line * this.lineHeightVp;
const capPaperH: number = this.paperVisibleTargetVp();
const capTop: number = this.carriageTopVp - capPaperH + 2;
if (this.paperTopTargetVp < capTop) {
  this.paperTopTargetVp = capTop > 0 ? capTop : 0;
}
```

- 纸顶本应随光标行每换行上移一个行高（`−cursorLine×lh`）。但 `capTop` 给它设了下限：纸顶一旦算到比 `capTop` 还高（值更小），就被钳回 `capTop`。注释原话就是“**封顶后纸顶不再上移**”。
- 平板验算：`carriageTopVp＝0.56×H≈603.6`，`capPaperH＝567.9`（见 1.2），`capTop≈603.6−567.9＋2＝37.7vp`。光标行到约 16–17 行时纸顶撞到这道下限，从此不再上移。

### 1.2 第二道：纸高封顶 567.9vp——纸长到这就不再长高

- `paperVisibleTargetVp()`：纸高＝`31＋lh×行数＋6`，再钳到 `cap＝306×(Pw/220)`。平板 `Pw＝408.3`，`cap＝567.9vp`。纸高到 567.9vp 就不再长。
- 两道合起来的后果（纸顶坐标系里算）：封顶前纸底恒定（`paperTop＋paperGrowVp＝561.6vp`，纸只向上长）；纸顶撞到 `capTop` 后，纸顶不动、纸高还在长（向 567.9vp 顶），**纸底＝`capTop＋paperGrowVp` 只能往下走**，直到纸高也顶满、纸底停在 `capTop＋567.9＝605.6vp`。纸底一共向下挪了 **44vp**（约 104px）——这就是用户看到的“占满上半部后转为向下延伸”。下半张纸（当前行附近）被顶进字篮井/键盘区。
- 批 68 的视口锚定（纸底钉视口底）没错，但它钉的是**渲染位置**；这两道封顶钉的是**纸顶与纸高这两个量**，纸顶上不去、纸高长不满，纸在内容上就“长不上去、只能往下长”。必须把两道都撤掉，纸才能一直向上出屏。

### 1.3 为什么撤封顶是安全的

- 纸高封顶的原始理由是保纸的宽高比（`Pw/纸高＝0.7183`，与贴图 `1484×2066` 一致，Fill 不拉变形）。但纸是数字纸、不是物理纸：**纸高应由内容（行数）决定，不应由贴图宽高比决定**。撤封顶后长纸的贴图会在纵向略拉伸——纸面主体是纯色奶油（`#faf8f2`），纹理很淡，拉伸几乎不可见，可接受；桌面端若实测拉伸刺眼，可改贴图为纵向平铺（另行记账，不在本批）。
- 单张纸不会无限长：文档满 20 行会自动换纸（批 68 自检已证 `sheet count -> 20/20` 触发 `paperChange`），所以一张纸最多约 609vp（20 行），撤封顶后纸顶最多到 `375.9−609＝−233vp`（屏幕上沿之上 233vp），不会失控。
- `paperScroll26()`（光标跟随）不受影响：纸高放开后，纸随内容长高、光标始终在纸内，`scrollYVp` 自然为 0；只有纸高被封顶时才需要它顶内容上移。撤封顶后它退化为 0，是对的（纸长高了就不需要卷动）。

## 2. 修法（两处删除，都是“撤封顶”）

### 2.1 撤纸顶下限 `capTop`（`recalcPaperHeight()`）

- 删掉这段钳制（整段删除，不留 `capTop` 变量）：
  ```ts
  const capTop: number = this.carriageTopVp - capPaperH + 2;
  if (this.paperTopTargetVp < capTop) {
    this.paperTopTargetVp = capTop > 0 ? capTop : 0;
  }
  ```
- 此后 `paperTopTargetVp ＝ carriageTopVp − paperBandBase − cursorLine×lh`，**没有任何下限**：光标行每加一行，纸顶上移一个行高，可以一直上移到负值（屏幕上沿之上），永不回头。
- `paperTopVp` 仍由 `paperTopTargetVp` 赋值（动画路径不变），只不再被钳。

### 2.2 撤纸高封顶（`paperVisibleTargetVp()`）

- 删掉封顶钳制，纸高只由内容决定：
  ```ts
  const v: number = 31 + this.lineHeightVp * lines + 6;
  return v > 58 ? v : 58;   // 只保留下限 58（1 行纸不塌掉），不再钳上限
  ```
  （删掉 `machineW／designPw／cap` 三行与 `v < cap ? … : cap` 这一支。）
- 此后 `paperGrowVp ＝ 31＋lh×行数＋6`，随行数一直长（20 行约 609vp）。纸顶＝视口底 − 纸高，随之上移、可以一直超出屏幕上沿。
- 不改行高/字号/纸宽/边距；不改 `paperScroll26()` 的公式（它自然退化为 0）；不改 20 行自动换纸。

### 2.3 自适应总则（本批硬要求）

- 本批是**删除**两道写死的封顶，不引入任何新常数。纸顶、纸高此后只由光标行与行数这两个内容量推导；纸底仍由批 68 的视口锚定（`paperAreaH()`）钉在视口底。**纸只向上长，永不向下伸**。
