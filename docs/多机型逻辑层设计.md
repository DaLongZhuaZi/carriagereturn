# 多机型逻辑层设计（1930s 落地批）

> 目标：换机（1920s ↔ 1930s）时，打字视图的分层件（滚筒／中央件／拨杆／压纸卷／底座／字杆篮／字杆）全部换成当前机型的素材与几何，不再是 1920s 一套打天下。
> 事实源：1930s 素材已入仓（`layers/1930s-portable/` 7 件＋`typebar/1930s-portable-*.png` 3 件，`08aa905`）；锚点实测值见 `docs/素材分层锚点表.md` 的 1930s 节。
> 范围：本批只做 1930s 接入逻辑层（1920s 回归零像素）；1950s／1960s 素材未到，逻辑上留好口子、不硬编造。

## 2. 铁约束：`$rawfile()` 只接受编译期字符串常量

MachineCatalog.ets 文件头已写明：`$rawfile()` 只接受编译期字符串常量，组件里用 if/else 静态分支取图，**不要拼变量**。即下面这种写法是**不允许**的：

```arkts
// ❌ 禁止：运行时拼路径，$rawfile 编译期求值会失败
Image($rawfile('layers/' + this.layerDir + '/lever.png'))
```

**唯一合法写法是按 `MachineKind` 静态分支**（`CarriageStrip.ets` 已是现成范例：它接 `machineKind` @Prop，用 `if (1920s) … else if (1930s) …` 分支取各机 `carriage/*-carriage-strip.png`）：

```arkts
// ✅ 合法：静态分支，每个分支都是编译期常量
if (this.machineKind === MachineKind.PORTABLE_1930S) {
  Image($rawfile('layers/1930s-portable/lever.png'))
} else {
  Image($rawfile('layers/1920s-upright/lever.png'))
}
```

几何数（宽高比、锚点比例）是纯数字，**不受**此约束，可以进 `MachineSpec` 按机型取数。路径与几何分两条路走，不可混为一谈。

## 3. 设计原则

1. **几何进目录，路径走分支**：所有按机型变化的数字（宽高比、锚点、孔位）进 `MachineSpec` 字段，Index 从 `findMachine(machineKind)` 取数后当 @Prop 传给组件；所有图片路径用 `MachineKind` 静态分支，不拼字符串。
2. **组件不自己查全局机型**：`CarriageLayers`／`LeverLayer`／`TypebarLayer` 只认传入的 `machineKind` @Prop ＋几何 @Props，不读全局状态、不自己 `findMachine`。换机时 Index 重建传参即可。
3. **1920s 零回归**：1920s 的字段值与现行写死值完全一致；改完后 1920s 打字视图截图与改前分毫不差（平板＋手机各一遍）。
4. **1930s 先通后精**：本批先做到“换机后 1930s 分层件正确加载、位置正确、不错位、不出屏”；细部视觉（色调、压暗、阴影）后续再调，不在本批扩范围。
5. **1950s／1960s 留口子**：分支里对未到的机型走 1920s 分支（或 `CarriageStrip` 兜底），不许用 1930s 素材顶替，不许编造不存在的路径。

## 10. 换机后「继续写作」回到收藏页／仍加载 1920s（2026-11-08 用户报，待修）

### 现象

1. 收藏页点某机型 →「使用这台机器」→ 回主页点「继续写作」→ 显示收藏页（不是打字机）。
2. 再回主页点「继续写作」→ 打字机打开了，但机型是 1920s（不是刚换的机型）。

### 根因 A：导航栈失同步（回到收藏页）

- `CollectionDetailPage` 的「使用这台机器」（Index.ets 约 3424 行 `onSetCurrent`）只手动关了两个布尔量（`collectionDetailKind = ''`、`collectionOpen = false`），**没有把 'collection'／'collectiondetail' 从 `navStack` 里弹掉**。栈仍是 `['home', 'collection', 'collectiondetail']`。
- 下一次任何 `pushPage`／`popPage` 都会调 `syncFromStack()`（约 785 行），它用 `has()`（`indexOf >= 0`，查整条栈不是栈顶）重算 `collectionOpen = has('collection') || has('collectiondetail')` → **true**。收藏页覆盖层重新渲染，盖在打字机之上（build 里覆盖层在主视图之后绘制）。
- 修法：`onSetCurrent` 里把手动关布尔量的两行改成 `this.popTo('home')`。`popTo` 把栈截成 `['home']` 再调 `syncFromStack()`，`collectionOpen` 与 `collectionDetailKind` 会被正确重算。

### 根因 B：机型选择没落盘（依然加载 1920s）

- 机型选择只存在两个地方：① `Index.machineKind`（内存）；② 当前文档的 `meta.machine`（`DocModel.setMachine` 改内存，`flushSave()` 存盘）。**`PrefKeys` 里没有 MACHINE 键**。
- `flushSave()`（约 2571 行）守卫 `if (!docStore.isReady() || this.docModel.isEmpty()) return;`——**空纸不存**。在空纸上换机，换机动作根本没落盘。
- `loadDocument()`（约 2625 行）`this.machineKind = data.meta.machine`——从文档存盘的机型覆盖当前机型。文档存的是 1920s，换机就被冲回 1920s。
- 启动时约 929 行 `this.applyMachine(DEFAULT_MACHINE)`——每次冷启动都回 1920s。
- 修法（机型改成全局偏好，文档不再覆盖）：
  1. `AppPreferences.ets` 的 `PrefKeys` 加 `MACHINE: string = 'machine'`。
  2. `applyMachine(kind)` 里加 `appPreferences.setString(PrefKeys.MACHINE, kind as string)`。
  3. 启动时约 929 行改成从偏好读机型（读不到回落 `DEFAULT_MACHINE`），不要每次都 `applyMachine(DEFAULT_MACHINE)`。
  4. `loadDocument()` 里删掉 `this.machineKind = data.meta.machine;`，改成 `this.docModel.setMachine(this.machineKind)`（文档沿用当前全局机型，下次保存时写回）。纸张／色带那两行不动。
- 语义变化（须知）：文档不再“记住自己的机型”；机型是全局 App 设置。`meta.machine` 仍在保存时写回（文档列表可显示），但加载时不再驱动机型。

### 验收（识屏为准）

- 收藏页换到 1930s → 点「使用这台机器」→ 回主页点「继续写作」→ 直接进打字机（不是收藏页），机型是 1930s。
- 再回主页点「继续写作」→ 仍是 1930s。
- 杀掉 App 重进 → 机型仍是 1930s（不是 1920s）。
- 换回 1920s 后点「继续写作」→ 1920s，正常。
- 1920s 回归：打字／换行／退行／换纸正常。

### 现象（截图量测，手机 Nova，图 1600×2560，纵向 1px≈0.321vp）

- 纸顶约 265vp，纸底（滚筒）约 410vp；纸面区上方约 200vp 空暗底（§19 设计如此，见末尾）。
- 底座是一大块深色板（实测可见约 43vp，但按 `baseW/baseRailAspect` 算应为 117vp——超出纸面区被裁，见根因 D）。
- 拨杆在右侧基本看不见；中央件三角拱顶与 T 形窗框像脱开的两件。

### 根因 A：拨杆支架图仍是 1920s（Index.ets 约 2891 行，桌面 7fd6305 漏改）

- `Image($rawfile('layers/1920s-upright/lever-pivot-bracket.png'))` 写死，没按机型分支。1930s 渲染的是 1920s 矩形板支架，但拨杆定位用的却是 1930s T 形支架几何（bracketAspect 1.2921、孔 0.519/0.199）——图被 `ImageFit.Fill` 压扁、销钉孔对不上拨杆支点，拨杆像脱开。
- 修法：按 `machineKind` 静态分支，1930s 取 `layers/1930s-portable/lever-pivot-bracket.png`，其余走 1920s 分支。

### 根因 B：`leverW()` 仍用 0.212（Index.ets 约 1561／1571 行，桌面 7fd6305 漏改）

- 平板 `carriageHeight × 1.84 × 0.212`、手机 `h × 0.212`，0.212 是 1920s 拨杆宽高比（536/2522）。1930s 应为 0.3264（711/2178）。
- 后果：1930s 拨杆宽只有 14.7vp（应为 22.6vp）；LeverLayer 内 `leverH = layerSizeVp / leverAspect`（0.3264）算出杆长只有 45vp（应为 69vp）——杆又细又短，深色杆在深色底上几乎看不见。
- 修法：两处 `0.212` 都改成 `findMachine(this.machineKind).leverAspect`。

### 根因 C：中央件宽度仍用 0.848（CarriageLayers.ets 约 315／320／325 行，桌面 7fd6305 漏改）

- 容器宽 `hc×1.5×0.848`、高 `hc×1.5`，0.848 是 1920s 中央件宽高比（1138/1342）。1930s 中央件是 1258×1153，宽高比 1.091（宽扁）。
- 后果：1930s 图用 `ImageFit.Contain` 塞进竖长容器，被压扁留白，窗位与拱顶错位，看上去像三角拱顶与 T 形窗框脱开。
- 修法：MachineSpec 加 `centralAspect: number`（1920s 0.848、1930s 1.091），三处 `0.848` 改用该字段（Index 传参进 CarriageLayers）。`centralWindowY` 已是 @Prop，不动。

### 根因 D：底座过高溢出纸面区（CarriageLayers.ets 约 253 行）

- 底座高 `baseW() / baseRailAspect`：手机 baseW≈347vp，1930s 比 2.95 → 117vp；1920s 比 7.56 → 46vp。1930s 底座顶在 `carriageTopVp+Hc/2+2`（手机约 324vp），底到约 441vp，超出纸面区（约 368vp）约 73vp，被容器裁掉——只见一大块深色板，底沿生硬截断。
- 修法（二选一，优先代码钳制）：底座高改为 `min(baseW()/baseRailAspect, Hc)`（1920s 约 46vp≈Hc 不变，1930s 钳到约 45vp），图用 `ImageFit.Cover`（横向裁切保高度，不压扁）。若钳后纹理仍显怪，再考虑把 1930s 底座素材重生成得更薄（另起，不在本批）。

### 不属于本批的（勿扩范围）

- 纸面上方约 200vp 空暗底：§19 定案（手机 carriageTop 系数 0.64＋10×行高下限 300vp），纸顶位置与 1920s 手机一致，不是 1930s 专属 bug。觉得空再单独调系数，不在本批。
- 纸底与滚筒交界有细线：1930s 纸与滚筒纹理色差比 1920s 大，过渡线更显眼，属观感微调，不在本批。

### 验收（识屏为准）

- 1930s 手机打 5 行：拨杆可见（细杆＋圆球顶，绕支架销钉孔转，不飘）、支架是 T 形（不是矩形板）、中央件是完整哥特拱（拱顶与窗框一体不脱开）、底座是窄条（不超纸面区、不盖字体条）、纸与滚筒交界无断开。
- 1920s 零回归（平板＋手机各打 5 行，截图与改前分毫不差）。
- 切回 1920s 后一切复原；1950s／1960s 仍是 CarriageStrip 兜底。
