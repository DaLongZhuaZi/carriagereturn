# 手机操作手册（桌面端自足操作规范）

> 立规背景：桌面端多次在手机操作上卡住后直接找用户（点一下、给个坐标），
> 而这些坐标本来都能从代码／截图／dump 里自己算出来。
> **铁律：永远不让用户帮你点、永远不让用户给你坐标。**
> 用户只做只有他能做的事（真机手感、声音、左边缘手势、读屏听感）。
> 坐标与方法一律自己取证、自己验证、记进本文件，下次直接用，不再重算。

## 0. 设备与坐标系

- 唯一测试设备：手机 ADA-AL00U（Nova 12 Ultra），USB 连接，target `2UCUT24724009680`。
- 屏幕：**1224×2776 px**，vp2px = **3.375**。所有坐标一律用**原生 px**（1224×2776），
  除非特别说明。截图是原生 1224×2776；录屏是 848×1920（缩放 ×0.693），
  视频里量的 px 要 ÷0.693 才是原生 px。
- 换算：px = vp × 3.375；vp = px ÷ 3.375。

## 1. 取坐标的梯子（按顺序走，不许跳级问用户）

1. **dumpLayout 优先**：`uitest dumpLayout`（或同等布局 dump）拿元素的 bounds，
   点中心。能 dump 的一律 dump，**不许目测**。
   - 主页底部导航 Row 的 id 是 `home__bottom_nav`，直接按 id 找。
2. **截图量测**：dump 不到时，截原生图，用像素阈值／行列统计量出元素的
   实际包围盒，点中心。**不许目测估数**——要算出来（亮像素行带、列带、
   边缘阶跃），量完把数写进 §3。
3. **代码算**：布局是确定性的。读源码算出几何（行高、列宽、边距、padding），
   再用一张截图锚定一个参照点（例如菜单卡片左缘、纸左缘），推出其余点。
   例：AppMenu 三项各 48vp=162px，行距 162px；主页底部导航五项各 layoutWeight(1)，
   每项宽 1224/5=244.8px。
4. **hilog 验**：点完立刻截屏＋dump＋看 hilog，确认动作生效（onPick／页面切换／
   落字）。没生效就诊断（见 §2），**不许直接找用户**。

## 2. 点完没反应时的诊断顺序（不许跳过）

1. 截图确认：点的是不是目标元素（行带／列带对不对，差一行就是 162px）。
2. 坐标空间：确认用的 px 是原生 1224×2776，不是用视频 848×1920 的数直接点。
3. 遮罩：菜单有全屏透明点透层，点在卡片外（x<卡片左缘 或 x>卡片右缘，
   或 y 在卡片外）只会关菜单、不导航。点必须落在卡片内、目标行内。
4. 入场动画：菜单出现有 160ms 淡入＋缩放 0.96→1＋上移 4vp。菜单刚开就点会打偏，
   **开菜单后等 ≥200ms 再点**。
5. 点按方式：优先用 **uinput 点按**（快速连打已证可靠）；uitest click 偶发整屏失效，
   失效时 `aa force-stop`＋重启 App 再试，**不许因此找用户**。
6. 再试一次：按 dump 的 bounds 中心重打一次。两次都失败才在记录里写清
   "试过的方法＋原文错误＋dump/截图证据"，报阻塞——**阻塞也不等于找用户点**，
   等用户定夺下一步（例如换验证方式），不是让他上手操作。

### 3.6 屏幕常亮与锁屏（2026-11-16 实测）

- 常亮要两条一起下：`power-shell timeout -o 3600000`（override 熄屏时间）＋ `power-shell wakeup`；
  只 wakeup 会被 AOD/睡眠模式吃掉，几秒后又暗。
- **锁屏时 `aa start` 必失败**：`Error Code:10106102 Error Message:The device screen is locked during the application launch, unlock screen failed`
  （`Error cause: The current mode is developer mode, and the screen cannot be unlocked automatically`）。
- 锁屏只能由用户指纹/密码解：本轮试过 `uinput -K -d 18 -u 18`（切亮/AOD）、`uitest uiInput swipe`、
  `uitest uiInput dircFling 2/3`、`uinput -T -g` 上滑、`aa start` —— 全部只能唤醒或停在 AOD，解锁不成立。
- 拖拽语法：`uinput -T -g x1 y1 x2 y2 PRESS TOTAL`，要求 `PRESS≥500` 且 `TOTAL-PRESS≥500`
  （例 `-g 1050 1080 1050 1520 500 1300` → 真拖、产生 Move）；`uinput -T -m` 的 keep time 传 0/5 报
  `invalid keep times`，不要用它做拖动。

- 每验出一个新坐标／新方法，**当批就写进 §3**（附测自哪张截图／哪个 dump），
  不许只记在自检记录里——自检记录是流水账，本文件是操作手册。

## 5. 方法禁令：不许质疑已定方法、不许让用户选方法（2026-11-15 立规）

- **已定的方法是定案，不是讨论稿**。录屏技能（`skills/hdc-screenrecord/SKILL.md`）、
  本手册的坐标梯子、三步法（代码 rect＋裁剪在位＋前后差分）、16 号稿 §3.3 的
  hilog 取证口径，都是已经设计好、用户批准过的。**不许质疑、不许重新谈判、
  不许拿给用户二选一**。
- **方法到限了怎么办**：走设计里已经写好的兜底，记不符点，不许停下来问用户。
  具体到时序验收：16 号稿 §3.3 与 line 101/250/252 已定——
  "Canvas 化后观测值就是插值本身，动画取证改靠 hilog 打点（帧率采样＋关键帧打点）
  与 screenCap 中途截图"，screenCap 单帧 400–500ms 大于 350ms 动画窗口、
  连拍不可靠。**视频（VFR，约 35–44fps）从来不是毫秒计时工具**，
  它只负责视觉确认（拱动了、字车弹簧了、方向对了、无跳变）。
  70/90/200/300ms 的计时一律用 hilog 帧时钟打点量（手机 Canvas 约 120fps，
  一帧约 8ms，70ms 约 8 帧、90ms 约 11 帧，精度够），容差 ±20ms。
  录屏里分不清 70ms 不是方法坏了，是拿错了工具——换工具，不许问用户。
- **用户只定工作、不定方法**。用户决定"做什么、做到什么算过、哪个优先级"，
  以及只有他能做的事（真机手感、声音、左边缘手势、读屏听感）。
  "用什么方法验"、"两种证据取哪种"、"录屏还是 hilog"，是 agent 自己的活，
  在已批准的方法里选，选完在记录里写清理由。**把方法选择题推给用户，等于把
  自己的工作推给用户**，不许再出现。
- 真正的方法缺口（已批准的方法里确实没有、且兜底也走不通），才记阻塞：
  写清"试过的方法＋原文错误／证据＋为什么已批准的方法走不通"，等用户定夺
  **下一步做什么**——不是让他选方法。
- **时序验收具体做法（2026-11-15 定案，已写入，不许再问）**：
  帧时钟每帧有时间戳。在动画起点（animateArch 被调／stepCarriageRight 被调）
  记一条 hilog（触发类型、目标值、duration 参数 90/200/300/70）；
  在值首次到达目标（误差 ±1vp 内）时再记一条。实测时长 = 到达时间 − 起点时间。
  现有代码没记这两条就补打点（验证用打点，改完重建），不许改动画本身。
  要量的数：拱 10 次落字各 90ms、退行 200ms、换行释放 200ms、换纸 300ms；
  删除弹簧 70ms。容差 ±20ms。视频只作视觉确认。
  **开工前必须先 pull 到最新 main**——定案写在仓里，不 pull 就看不到，
  看不到就还会把已经定了的问题再问一遍。
- **ArkUI `@Prop @Watch` 不与同批 prop 原子同步（2026-11-16 实测，血泪教训）**：
  tick 值与伴随的目标 prop 在同一任务里写入，watch 仍可能先跑、读到**旧目标**
  （实录 `paper instant top=206.0 box=96.0`，把刚起的换纸第 1 段拍回原位）。
  定死口径：tick 通道一律「watch 只登记 pending，**下一帧 onframe** 统一读目标起段」；
  纸的位置也只由纸段 tick 决定，`onDocChanged` 不许拿逻辑 prop 覆盖渲染值。
- **持续逐帧全屏重绘会打爆 GPU 预算（2026-11-16 实测）**：真机按住拨杆逐帧画 2–3s 即被系统杀，`RENDER_MEMORY_OVER_ERROR: gpu[≈2.156GB]`（硬顶，kill_id 2010）；空闲或「按住但无 Move」不被杀 → 是**绘制次数**驱动。定死：拖拽期只在该帧有 Move 时上屏（脏标记），空帧不画；渐变对象按几何缓存，不许每帧 `createLinearGradient`。
- **数帧不看 dt（2026-11-16 定案）**：验收「到底有没有动画」要数 Canvas 的 draw frame 打点（每次真正上屏一条），`anim arrive` 的 dt 只证明插值时长、不证明渲染帧数。实测换行窗 76 帧/900ms、退行 41 帧、绘制间隔 p50=8ms（≈120Hz）；一次会话约 **200 次 draw** 的 GPU 预算（超过即 `RENDER_MEMORY_OVER_ERROR` 被杀），取证窗口要控在 150 draw 以内。
