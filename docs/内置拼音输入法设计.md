# 内置拼音输入法设计（回车 CarriageReturn）

**本稿为内置拼音输入法的事实源。** 界面重设计稿 §7.2 的中文输入部分以本稿为准：原“双通道”（英文自绘键／中文系统输入法）改为“三通道”——英文自绘键、中文系统输入法、中文内置拼音。

## 0. 决策

- **双线共存**：系统输入法通道保留；**内置拼音为默认引擎**（2026-11-07 用户拍板）。
- 内置拼音既是默认体验也是补充措施：系统通道是 fallback，设置里一 tap 切回。
- v1 范围：全拼输入、候选栏、组词状态机、词库管线、引擎单测。**不做**：模糊音、用户词库持久化、长句预测、双拼／九键、云端联想。
- 背景结论（不再论证）：系统输入法引擎路线走不通——IME Kit 客户端 API 无候选词查询、无向输入法发按键的接口；`customKeyboard` 是替换系统键盘不是前端；`attach(false)` 藏了键盘就没了输入源。唯一可行路线是 App 内自建拼音引擎。
- 质量预期（先说清楚）：v1 弱于华为／搜狗输入法——词库小、无云端、无长句预测、无模糊音、无自学习持久化。换来的是全程无系统键盘、候选栏长在打字机里、全离线、风格统一。

## 1. 模式与切换

- `langZh` 不动（中／EN 语言切换）。
- 新增 `cnEngine: 'builtin' | 'system'`，持久化进 `AppPreferences`（补 `getString`／`setString` ＋ `PrefKeys.CN_ENGINE`），默认 `'builtin'`。
- 设置页加“中文输入”行（放在“删除方式”之下），点切内置／系统。**必须走 AppPreferences 持久化**，不许用页面内部 `@State`——设置页其余开关不持久化是已知缺口，本行不许重蹈。
- `applyChineseMode(on)` 按引擎分叉：system 走现有 attach 通道；builtin 不 attach、不弹系统键盘、显示候选栏、键区当拼音键盘。
- 悬浮 A 键只在 system 模式出现（builtin 没有系统键盘盖住底行，不需要它）；`kbShift` 只在 system 模式有意义，builtin 下恒为 0。
- `leaveChinese()`：builtin 下先按 §4 退出规则提交首选候选，再清组词、关候选栏。

### 2.2 管线

- 脚本：`tools/build-pinyin-dict.py`（Python 3，只用标准库＋pip 装 pypinyin；不用 pip 就改走 phrase-pinyin-data 与 pinyin-data 两个仓库的原始数据文件，任选一种，提交里写明选了哪种与为什么）。
- 步骤：下载三源（钉版本＋SHA-256）→ 解析 jieba 词频 → 每词读音：pypinyin 词组覆盖优先，否则单字主读音拼接 → 按词频排序截前 8 万 → 输出两 JSON → 写 `DICT-ATTRIBUTION.md`（来源、许可、版本、SHA-256，与 `SOUND-ATTRIBUTION.md` 同格式）。**v2（§16）起为四源**：加 CC-CEDICT 全量并入（去重、排在 jieba 词之后、只取 2–4 字词）＋补录表＋HOT 置顶；词表预算 2.5MB→3MB。
- 输出：`entry/src/main/resources/rawfile/dict/pinyin-words.json`（`{拼音串: [词...]}`，数组即词频序）与 `pinyin-chars.json`（`{音节: [字...]}`）。体积预算：字表 ≤400KB，词表 ≤2.5MB；超了先截词频尾部，不改格式。**v2：词表 ≤3MB（实测 2.53MB）。**
- 加载：字表启动时异步加载；词表首次进内置中文模式时懒加载；加载失败不崩，只退单字候选＋候选栏提示“词库加载失败，仅单字”。加载方式复用 `KeymapModel.ets` 的 `readRawTextSync` 范式（词库 JSON 用异步版读，不许在主线程同步解析几 MB）。

## 3. 引擎

- 新文件 `entry/src/main/ets/services/PinyinEngine.ets`：`PinyinEngine` ＋ `PinyinSession`。**纯 TypeScript，不引任何鸿蒙 API、不含 `@State`／装饰器，同一文件必须能在 Node 下跑单测。**
- 数据：音节表（约 420 个合法音节）、`charMap: Map<音节, 字[]>`、`wordMap: Map<拼音串, 词[]>`（数组已按频排好）。
- 切分：输入字母串 DP／回溯拆音节（最长音节 6 字母）；每种切分查词表；候选＝词＋单字回退，按频取前 N。
- 排序：词频预排序＋用户选词提频（L0，v1 只记内存）。
- 模糊音 v1 不做；扩展点：切分时音节展开走一张 `fuzzyMap`，以后加模糊音只换表不重构。
- 性能口径：精确 Map 查＋DP，每击键远低于 1ms；FST 不需要（40 万条前缀搜索才需要，我们只要精确键查）。

## 4. 状态机与按键语义

- `PinyinSession` 三态：空闲 → 组词中（有拼音串）→ 选词后剩余字母继续组词。
- 拦截点：`Index.ets` 的 `onCapDown`；`queueChar`／`commitChar`／`onDelete`／`onNewline` 全部复用。
- `v` 是 ü（`lv`、`nv`）。

| 按键 | 组词中 | 组词为空 |
|---|---|---|
| 字母 a–z | 追加拼音串，重新切分，候选栏刷新；预编辑串复用 `cnPreview` Span（浅色＋下划线） | 开始组词，不落字 |
| 退格 | 删最后一个字母 | 走现有 `onDelete` |
| 空格 | 选首选候选 | 走现有空格直通 |
| 数字 1–9 | 选第 N 个候选 | 正常落数字 |
| 数字 0 | 下一页候选 | 正常落 `0` |
| 换行 | 先把拼音串按原样上屏（`nihao` → 拉丁字母 `nihao`），下一次换行才是真换行 | 走现有 `onNewline` |
| Shift＋字母 | 先提交首选候选，再按原样打大写字母（中文里插英文的逃生口） | 现有 Shift 行为 |
| 字符键／中 EN 切换／换纸／换机／离页 | **统一规则：退出组词时提交首选候选**（换行除外），绝不丢已敲字母 | — |
| 点候选词 | 走 `enqueueChinese`（40ms 逐字落字）；只消耗该词覆盖的音节，剩余字母继续组词（`nihaoma` 选“你好”后 `ma` 留下） | — |

## 11. 词库与个性化 v1.5（2026-11-07 用户定继续优化）

### 11.1 前缀候选（未打完也有候选）

- 现状缺口：`candidates('nih')` 返回空（无完整切分），栏里只剩拼音串、没有 chip——用户会误以为输入法坏了（桌面端 3de8b43 实测确认此状态）。
- 改法：`candidates()` 里整串无合法切分时，退到**最长合法前缀**出候选（`nih` → 按 `ni` 出候选，余下 `h` 留在拼音串里）；`Candidate.pinyin` 已带“消费了几个音节”的拼音串，选词后余量字母继续组词（现有 `pick()` 逻辑不用改）。
- 验收：`nih`、`niha`、`zhongg` 都有候选；选词后余量正确。

### 11.2 选词学习（L0，持久化）

- 现状缺口：`PinyinSession.picked` 只记数，从不参与排序、从不落盘——选了等于白选。
- 改法：选词时记 `(拼音串, 词, 次数)`；排序时同学习词置顶（同拼音串内按次数＋新近排）；落盘走 `AppPreferences`（`getString`／`setString` 已有）存 JSON，上限约 300 条、LRU 淘汰；保存节流（离开中文模式时存＋每选 10 次存一次，不许每击键都写盘）。
- 隐私：只存本地，零遥测；拼音设置页里给“清除学习记录”。

### 11.3 模糊音（开关，默认关）

- 模糊表（v1.5 只做这 8 组）：zh↔z、ch↔c、sh↔s、in↔ing、en↔eng、an↔ang、n↔l、f↔h。
- 实现：切分时音节按模糊表展开（`segments()` 入参加模糊开关）；开关存在 `AppPreferences`（默认关），放拼音设置页。
- 验收：每组各一例（如 `zhao`/`zao` 都能出“找”，`nin`/`ning` 都能出“您”）。

### 11.4 我的词库（自定义词组）

- 加词：用户在拼音设置页输入一个词组（中文），拼音由引擎单字主读音自动推导（多音字取首选读音，v1.5 不做人工改音）；存 `AppPreferences`（与学习记录分开的键），上限约 200 条；加载时并进 `wordMap`，同拼音串内置顶。
- 管理：列表＋删除；重名／已在内置词库里的词照常收（置顶即可，不报错）。
- 验收：加“大龙爪子”→ 打 `dalongzhua zi` 能选中上屏；删后不再出现；重启后还在。

### 11.5 词表质量过滤（管线）

- 现状：8 万词按 jieba 词频截断，仍可能混进生僻词（chars 表已用 jieba 单字词频重排过，见 3de8b43；words 表未做同等过滤）。
- 改法：`tools/build-pinyin-dict.py` 里加过滤——整词全是生僻字（不在常用字表内）或词频低于下限的去掉；重新生成后词条数、体积记入提交，抽查 `nihao→你好`、`zhongguo→中国` 不变。
- 不在本批：声母缩写（`nh`→你好，切分歧义会爆炸）、上下文联想（bigram，参考 inputx-ngram，排以后）。

### 11.6 拼音设置页（新页）

- 入口：设置页“中文输入”行之下加“拼音设置”行，`pushPage('pinyinsettings')`；按 §2.10 沉浸式＋PageShell 走。
- 内容：模糊拼音 开／关；我的词库（条数＋管理入口）；清除学习记录；词库信息（版本、词条数、更新日期，随管线生成时写入）。

## 12. 中文删除错行修复（2026-11-07 用户报）

### 12.1 根因（读码定位）

- **合并行不重排**：行首退格时 `DocModelCore.backspace()` 把本行并入上一行（一行变两行宽），`syncRows()` 只把逻辑行 1:1 映成显示行、**不重排**——合并后的超宽行整行显示在纸上（超纸宽、被裁），这是错行的第一半。
- **删后纸不动**：`onDelete()` 只调 `syncRows()`／`animateGuide()`／`stepCarriageRight()`，**不调 `recalcPaperHeight()`**；纸顶仍由旧光标行派生——合并后光标行减 1，纸却没动，纸顶与光标行错开整整一行（打击行上显示的是下一行的字），这是错行的第二半。
- **下一字再错一次**：合并行已超宽，下一字落字时 `commitChar` 的位置触发换行在光标处断行（不是纸边距处），断点落在词中间，错行固化。
- 为什么中文重：中文一行约 16 字（英文约 26 字），中文文档行边界多约 1.6 倍，行首合并更容易撞上；且 `charsPerLine()` 是英文口径（26 字），中文下计数备份换行永远等不到触发，拦不住超宽行。

### 12.2 修法

1. **先复现**：打两行满行中文 → 光标放第二行行首 → 退格一次（合并）→ 截图＋日志（光标行、总行数、`paperTopVp` 前后）。确认合并行超宽、纸顶未动，再修。
2. **合并后重排**：新增 `rewrapOverwideLines()`（放 Index，用 `charWidthVp` 的宽度口径，与 `commitChar` 的位置触发同算法）：删后若行数变了，把超宽行按纸宽断成多行，光标落到正确位置（合并点所在的那一段末尾）。恢复不变量“逻辑行不超纸宽”（打字路径本来就维持这条不变量，删除路径也要）。
3. **删后重算纸顶**：`onDelete()` 里行数变了就 `paperAnimateNext = true` 再调 `recalcPaperHeight()`（与 `onBackLine` 同口径，纸滑过去不许跳变）；行数没变时调了也是无操作，不用分叉。
4. **`charsPerLine()` 按语言算**：中文模式用 CJK 字宽（约 16 字），英文用英文字宽；行末铃（`insertText` 的 `remaining <= 8`）随之回到正确时机。
5. **核对宽度口径（诊断项）**：用现成的 `charTrace` 日志（`measW` 实测 vs `accumW` 累计）核一整行中文的实测宽与累计宽；差值超 10vp 再议 `advCjkVp` 的取值，不许没证据就改字宽。

### 12.3 验收

- 复现用例：两行满行中文，第二行行首退格一次 → 合并行在纸宽处断开、光标行正好落在打击行、纸滑动无跳变；再连续退格跨 3 个行边界，无错行。
- 回归：英文同样用例；中／EN 切换后删除；系统模式与内置模式删除；XXX 覆盖删除不受影响（它不合并行）。
- 不在本批：行高口径（主纸走 `PaperStage`，行高直接取 `lineHeightVp`，与定位同口径——此前怀疑的 1.7 倍率漂移不存在，`components/PaperSheet.ets` 的 1.7 不是主纸用的）；emoji 等 BMP 外字符的代理对删除（另记，不在本批）。

### 13.1 待修 bug（5 项，沙箱独立复核发现）

**① 模糊音韵母对失效（高优先）**
- 现状：`fuzzyVariants` 只做**前缀**替换，声母对（zh/z、ch/c、sh/s、n/l、f/h）通，韵母对（in/ing、en/eng、an/ang）对带声母的音节全失效。沙箱实测（模糊音开）：`nin` 无“宁”、`ban` 无“帮”、`chen` 无“成”。
- 根因：`nin` 的韵母 `in` 在音节尾部，`startsWith('in')` 永远匹配不到。
- 修法：模糊展开分两类——声母对做前缀替换，韵母对做**后缀替换**（音节尾部 `in`→`ing`、`en`→`eng`、`an`→`ang`，反向亦然）；裸韵母（`an` 本身）两种替换结果一致，不许重复。
- 单测：改成真断言——打 `nin` 必须出“宁”、打 `ban` 必须出“帮”、打 `chen` 必须出“成”、打 `ning` 必须出“您”（只断言“两侧都有候选”测不出这个 bug，以后不许这样写断言）。
- 真机验收：开模糊音，打 `nin` 栏里出现“宁”且可点选；关模糊音，打 `nin` 不再出现“宁”。

**② 词表过滤误伤常用词（高优先）**
- 现状：8 万→5.1 万词时整键删了 16 个键，包括**咖啡、垃圾、槟榔、傀儡、咆哮、喃喃、邂逅、妞妞**等常用词（沙箱新旧词库对照验真）。
- 根因：规则“整词全是生僻字（单字词频<50）”按单字词频判——咖/啡、垃/圾、槟/榔这类字只成词、不单用，被当成了生僻字。
- 修法：删词改**双条件**（单字全生僻 **且** 词频低于下限才删，任一条件不满足就留）；另加白名单（小表，人工维护，种子：咖啡、垃圾、槟榔、傀儡、咆哮、喃喃、邂逅、妞妞、鹧鸪、这股，以及本 App 自己的词：**回车、输入法**——这两个旧表就缺，不是一并补）；管线跑完打印被删的键列表，**人工过一遍再提交**（本批就是抽查太少漏掉的）。
- 验收：重新生成后 `kafei→咖啡`、`laji→垃圾`、`xiehou→邂逅`、`huiche→回车`、`shurufa→输入法` 都在；词条数、体积记入提交。

**③ 单字排序仍有漏网**
- 现状：`ni`→你、`shi`→是已修好，但 `mo` 首位仍是生僻字**銆**（`mo`→銆、末、摸、魔）。jieba 单字词频排序在个别音节上有数据 quirks。
- 修法：主排序改用 **《通用规范汉字表》一级字表（2500 字）＋二级字表（1000 字）的顺序**，表外字按 jieba 词频排后；字表来源文件进 `tools/` 并写明出处。
- 验收：抽查 20 个音节的首字都在 3500 表内；`mo` 首位是末/摸/魔之一、銆 沉底；`ni`→你 不变。

**④ 词库信息硬编码“8 万词”**

## 14. 多字落字连跳修复（2026-11-08 用户报）

### 14.1 现象

输入法选词上屏时，字按内容连跳多次（2 字词跳 2 次、4 字词跳 4 次）；字直接闪现、无字杆、无按键音；词尾跨过行末时，换行编排走完后剩下的字一次全闪出来。

### 14.2 根因（读码定位）

- **两条落字链**：英文走 `queueChar`→`strikeTick`→字杆 90ms 去程→`onArrive`→音＋落字（串行，快速连打约 110ms/字）；中文输入法走 `enqueueChinese`→40ms 定时器→`commitChar` 直落，**绕过字杆与音效**。
- **每字一跳**：`commitChar` 里 `stepCarriageLeft` 是 30ms `animateTo`，40ms 一发，动画互相打断；字直接插进文档（`syncRows` 重渲染），无击打过程；`commitChar` 里无 `playKey`，中文选词上屏全程静音——“字 1:1 永不丢”的规则被绕过。
- **紧循环泄洪**：换行／退行结束后的 `queuedChars` 释放是 `for (...) commitChar(q[i])` 同步循环——排队的字同一帧全落下。
- **兜底定时器口径错**：`queueChar` 的 200ms 兜底从入队起算；4 字词排队时第 3、4 字没等到字杆就被兜底直落（无杆无声），且顺序可能错。
- **乱序口径**：空格／退格／换行不走落字队列——词还在 40ms 排队时按空格，空格会插到词前面（`commitChar` 直接插在光标处）；退格同理可能删错字。

### 14.3 修法（一条落字队列）

1. 删 40ms `cnTimer`／`cnQueue`；`enqueueChinese` 改为逐字调 `queueChar`（进 `pendingChars`）；所有输入法落字入口（选词、提交首选、换行整串上屏、系统 `insertText`、锚点增量）都走这一条。
2. 1920s：字杆 `onArrive` 驱动（现有串行机制，快速连打 90ms 去程＋20ms 小回退≈110ms/字）；非 1920s 机：补一个 120ms 起搏器（队列非空时起、空时停，每跳落一字），同样串行。
3. 兜底重定口径：200ms 兜底只对队首字、且 200ms 内无 `onArrive` 才触发；触发后走正常落字链（音＋杆回调），不许直接 `commitChar`。
4. 换行／退行释放排队字：改成逐字重回 `queueChar`（走起搏／字杆），不许 `for` 循环直落。
5. 空格进队列：空格也走 `queueChar`；`onArrive` 时若落地字是空格播 `playSpace`（不播主键音）；删 `onCapDown` 空格分支的直接 `playSpace`＋直落，防一声两响与乱序。
6. 退格：队列非空时先取消队尾字（及其待击发），不碰文档；队列空时走正常 `onDelete`。系统锚点缩短同理。
7. 节奏：单字落地周期约 110–120ms（快于真人打字约 200ms/字，慢于 40ms 闪现）；每字必有字杆摆动＋音＋字车左进（纸只在换行时动），三者同帧、不许动画重叠。
8. 换行中途：字在换行编排期间仍进 `queuedChars`，释放时走同一条队列（见 4），不许换行后一次闪现。

### 14.4 验收

- 选 2 字词：字杆摆两次、两声、字车左进两次、每字间隔约 110ms（`strike metrics` 的 `avgGap` 作证）；选 4 字词同理 4 次；无直接闪现、无动画重叠（录屏逐帧：字杆每次回到 40° 以上再下一击）。
- 跨行选词：词尾跨过行末时换行编排走完、剩下的字逐字落下，不一次闪现。
- 词未落完按空格：空格落在词后，不插队；词未落完按退格：先取消队尾字，文档不动。
- 音：每字一音，无丢音（`soundCount` == 落字数）；快速连打走 transient 短音（现有规则）。
- 英文回归：快打一串字母，字杆串行、无丢音、无兜底 flush 日志（`droppedTicks` 不涨）。
- 非 1920s 机：选词同样逐字落下（120ms 起搏），不一次闪现。

### 14.5 不在本批

- 字杆篮扇面加回（拼装期隐藏，另议）；音效包按机器区分（排队项）；空格键本身的手感（已按 14.3⑤ 走队列）。

## 15. 删字后哥特拱停行末（2026-11-08 用户报）

### 15.1 现象

删中文时，哥特拱（中央件，x = `clampedStrikeXVp()`）停在行末不跟字走；只有换行／退行能让它归位。英文删字正常。

### 15.2 根因（两条，读码定位，需桌面真机复现区分）

- **机制 A（主因，§14 的副作用）**：§14 起中文落字走约 110ms/字的队列，`onDelete` 在 `pendingChars` 非空时只取消队尾一个排队字就返回，不碰文档。用户打完一个词立刻按退格（最常见的纠错时机），队里还有没落下的字——退格取消的是看不见的排队字，纸面文字和拱都不动。用户看到的就是“删了字，拱还停在行末”。英文不走队列，所以英文没这问题。换行／退行会让拱跳到新行，看起来“修好了”。
- **机制 B（次因，超宽行＋钳制）**：拱 x = `clampedStrikeXVp()`，`raw = 纸屏左 + marginH + 行宽`，钳制到 `limit = 纸右 − 旋钮半宽`。平板上行宽超过约 382vp（16 个汉字）就钳住；17 字以上的行，删一字反而让拱向右 creep（O 增大推 limit 右移），要连删两字以上才脱钳。超宽行来自：行首退格合并（v1.5 的 rewrap 只在 onDelete 的现代分支里、且只在行数变化时跑）、以及旧文档（`loadDocument` 不 rewrap、不重算 O，超宽行原样进纸）。v1.5 之前中文行能上 26 字，合并能到 32 字，这些行现在还在文档里。
- **附带**：`recalcTravel` 的 `charsPerLineNum` 是英文口径（约 26），`charsPerLine()` 已是分语言（中文约 16）——travelPerChar 中文应是 4vp，现在是 2.46vp，O 中文行永不饱和。不是拱 bug 的根因，但同一批修。

### 15.3 修法

1. **退格先落队**：`onDelete` 里 `pendingChars` 非空时，先把队里字同步落下（直接 `commitChar`，不播音、不摆杆，记日志 `del flush n=`），再走正常删除。一次退格＝可见文字少一字、拱左移一字宽，不丢输入。被取消的旧口径（只取消队尾）作废。
2. **载入重排**：`loadDocument` 里对全部行跑一遍 `rewrapOverwideLines`（超宽行按纸宽断开），再 `syncRows`。旧文档的超宽行进纸即修，不再靠用户删字脱钳。
3. **合并重排补口**：确认 onDelete 合并分支（现代模式）每次合并后都跑 rewrap（已有，补真机验证：两行满 16 字中文行首退格合并，必须拆成两行、拱回落到尾行末、纸顶 +39.5 不错行）。
4. **travelPerChar 分语言**：`recalcTravel` 的 `charsPerLineNum` 改按当前语言算（与 `charsPerLine()` 同口径），中文 travelPerChar ≈ 4vp。验收：中文打满一行 O 到 −64 饱和。
5. **钳制是安全网不是常态**：修完 2/3 后，正常文档里钳制不应再触发；诊断日志里 `raw > limit` 出现即记 `strike clamped`，桌面复现时先报有没有触发。

### 15.4 验收

- 场景 A：选 2 字词，200ms 内按退格——可见文字少一字（不是没变化），拱左移约一字宽；再按退格，下一字也少；不丢词里其他字（flush 落下的字都在）。
- 场景 B：打开含 26 字中文行的旧文档（或两行满行合并），删一字——拱左移，不停在行末、不向右 creep；载入时该行已被拆成两行（日志 rewrap）。
- 回归：英文删字拱左移；行首退格合并（B 连续退格跨 3 边界，纸顶每次 +39.5）；§14 落字仍逐字摆杆＋逐字一音（2 字词 2 摆 2 音，间隔约 110ms，dropped=0）。

### 15.5 不在本批

- 钳制 limit 本身的改动（修完 2/3 后不应再触发）；拱的 Y 向。

### 17.3 切换内置输入法卡死（2026-11-08 用户报，v2 严重问题，本批必修）

- 用户原话：切换内置输入法会导致 appfreeze，直接无响应。
- **根因（沙箱读码坐实，两段同步重活堵 UI 线程）**：
  1. **`Index.ets decodeUtf8`（约 543 行）是逐字节 JS 循环＋字符串拼接**（`out += String.fromCharCode(c)` 逐字节）。v2 词表 2.53MB＝约 250 万次循环拼接，v3 词表 5.23MB＝约 520 万次——单这一段就数秒。`ensurePinyinEngine`（约 394 行）在 `await getRawFileContent` 之后同步跑 `decodeUtf8`＋`JSON.parse`＋`fromData`，全在 UI 线程上，UI 在这几秒内完全不响应点按。
  2. **`PinyinEngine.load`（`fromData`）里的 `buildAbbrev()`（约 143 行）**：对每一个拼音键（v2 86,035 个，v3 177,615 个）调一次 `segments()`（DP 切分＋模糊展开）再调一次 `addAbbrevFor`，而 `addAbbrevFor` 里**每调一次就把该缩写列表全排一次序**（`list.sort` 按 wordRank，列表最长 200）。同一个缩写（如 nh）被几十个键反复重排——总计约 17 万次 DP 切分＋约 17 万次列表排序，全是同步 UI 线程。词表越大越卡：v1（77k 词）约 1–2 秒只是顿一下，v2（145k 词）数秒已是 appfreeze，v3（251k 词）不修会更糟。
  3. `JSON.parse`（5MB，约 50–200ms，原生）与 `sortedKeys.sort`（约 200–500ms）不是主因；`ensureBigrams`（扫文档）通常很快，不是主因。
- **修法（四件，桌面端做）**：
  1. **换掉 `decodeUtf8`**：改用平台原生 `@ohos.util` 的 `TextDecoder`（`new TextDecoder('utf-8').decode(bytes)`），原生解码比逐字节 JS 循环快一到两个量级。若当前 SDK 没有 TextDecoder，改成分块解码（每 64KB 一段 `String.fromCharCode.apply`，不许逐字节拼接）。验收：hilog 打点 `decode ms=`，v3 词表（5.23MB）解码须 <500ms。
  2. **修 `buildAbbrev`**：`addAbbrevFor` 里不许每调一次就排序——只收集（上限 200），全部键跑完后再对每个缩写列表排一次序并截 30（一个收尾循环）。`segments()` 的 DP 调用次数不变（每键一次是必需的，缩写要音节切分），但排序从约 17 万次降到约 1 万次（缩写个数）。验收：hilog 打点 `abbrev ms=` 与 `abbrev count=`，v3 词表建索引须 <1000ms。
  3. **预加载**：App 启动（或首次进打字机页）即在后台调 `ensurePinyinEngine()`（不阻塞启动，失败不崩），用户切中文时大概率已就绪；未就绪时切中文只显示加载态（候选栏显示「正在加载…」，不许无响应），加载完再出候选。
  4. **加载态不许卡死**：`ensurePinyinEngine` 全程不许在 UI 线程上连续跑超过一帧的同步重活；`fromData` 的建索引若仍超过一帧，拆成多段（每段约 5000 键）中间 `await` 让出事件循环，UI 保持响应。
- **验收（识屏，见 17.4）**：切中文后 2 秒内候选栏出现（截图为准）；切中文过程中点任意键有反应（截图前后对比有变化）；打 `nihao` 选你好落字正常。hilog 的 `pinyin engine ready` 只作辅助，不算完成。

## 18. 哥特拱移动全场景分析：退行删字拱不动＋卡住＋闪现（2026-11-08 用户报）

用户原话：删除功能在遇到退行时，哥特扣未正确移动到上一行末尾，而且之后再进行删除操作也一直卡在原位，并且哥特扣始终要平滑的移动不能闪现。要求完整分析检查各种情况下它的移动是否符合逻辑并且有动画。

### 18.1 拱位置公式（读码坐实，`27f529b` 时点）

- 哥特拱＝`CarriageLayers.ets` 的 `part === 'metal'` 中央件（`central-guide.png`），x 由 `@Prop strikeXVp` 定（Index 三处调用点统一传 `clampedStrikeXVp()`，约 2624／2646／2664 行）。
- `clampedStrikeXVp()`（Index 约 1501 行）：`raw = paperLeft + marginH + currentLineWidthVp()`，`limit = paperLeft + paperWidthVp − knobHalf`，`raw > limit` 时返回 `limit`（钳住），否则返回 `raw`。其中 `paperLeft = (stageWidth − paperWidthVp)/2 + carriageOffsetVp`。
- `currentLineWidthVp()`（约 1521 行）：取光标所在行**整行**文本（不是到光标为止）逐字 `charWidthVp` 累加。
- `guideXVp`（约 207 行）是另一件东西：固定在舞台中心的导件（`animateGuide` 只把它设成 `stageWidth*0.5`），不随光标移动。本节说的哥特拱是 `strikeXVp` 那件，不是 `guideXVp`。
- **关键：拱的移动由两路分量合成，口径不同**——① 行宽分量 `currentLineWidthVp()`：文本一变就瞬变（`syncRows` 重设 `@State rows` → 重渲染 → 新 `strikeXVp`，**无动画**）；② 字车偏移分量 `carriageOffsetVp`：经 `animateTo` 动画（打字 30ms 线性、删字 70ms 弹簧、换行回位 150ms、退行 250ms）。**行宽跳变是主导量（中文每字 24vp），偏移滑动只是小量（中文每字 4.0vp，§15 落地后分语言）。所以拱的每一次移动都是「大跳变＋小滑动」，跳变占主导＝闪现。**
- **CarriageLayers 的金属件 `.position()` 上没有任何 `.animation()` 修饰**（全文件 grep `animation` 为空）。拱本身从未被动画过；它动的平滑部分全靠 `carriageOffsetVp` 的动画顺带，行宽部分永远是瞬跳。
- **前置说明（§15 已落地，`9461aa3`，2026-11-08 15:12）**：桌面已做完 §15 四件事——onDelete 改同步落队（`del flush`）、loadDocument 加重排、`strike clamped` 日志、travel 分语言。**本节数字按 §15 落地后的口径算：中文 travelPerChar = 64/16 = 4.0vp（不是旧的 2.46vp），打满 16 字中文行后 O = −64（顶满 maxTravel）。** §15 的落队修法让「队列未落完时删」不再拱不动，但本节的退行／闪现／卡住三问题 §15 没动，仍在。

### 18.2 逐场景验算（平板数：stageW 673.7、paperW 444.6、margin 28、knobHalf 34.8、maxTravel 64、travelPerChar 4.0（中文，§15 后）、中文宽 24；钳阈值 lineW > 381.8vp 即 ≥16 中文字）

### 18.3 根因（三个读码坐实＋一个待验假设）

- **根因 1（闪现，全部场景）**：拱本身无动画。`strikeXVp` 是算出来的值，`CarriageLayers` 金属件 `.position()` 无 `.animation()`。行宽分量每变必瞬跳，打字／删字／退行／换行／载入／换纸全都闪现。用户「始终要平滑、不能闪现」的要求现在一条都不满足。
- **根因 2（退行后位置错，行首删合并）**：`onDelete` 合并后不重算 O。`recalcOffsetFromCursor()` 全仓只在启动时调一次（约 928 行），`onDelete`／`onBackLine`／`onNewline`／`loadDocument` 里全都没有。合并后光标在上一行末（offset 16，正确 O 应为 −64，§15 后 travel 分语言），但 O 只被 `stepCarriageRight` 拨了 ＋4.0，停在约 0。拱＝（base＋0）＋margin＋行宽，比正确位置偏右约 64vp，且被钳在右缘 limit（524.4），不是上一行真正的末尾（460.4）。**这就是「未正确移动到上一行末尾」。**显式退行键不犯这条（它自己算 `targetO`），只有行首删的合并路径犯。
- **根因 3（卡住，钳制遮住移动）**：合并／退行后拱落在钳制区时，`archX = limit = base＋O＋paperW−knobHalf`，只跟 O 有关、跟行宽无关。而 `stepCarriageRight` 每删只拨 O ＋4.0，且 O 钳在 ≤0——O 已到 0 时再删也不动。于是行宽在变短、拱的钳制值却不动，看起来就是「删了字、拱卡在原位」。理想情况下一段 ≤16 字中文行删 1 字即脱钳，但合并行超宽、或光标在行中（合并点）而非行末时，行宽迟迟不脱钳，卡住会延续多删。
- **待验假设（卡住若多删仍不脱钳）**：若桌面实测发现连续多删后 `strikeX` 目标值本身就不变（不是钳制问题），则是 `@Prop` 未传到 `CarriageLayers`（父重渲染未刷新子件）或某条删路径没调 `syncRows`。桌面须先打日志定性（见 §18.5 第 0 步），不许凭猜测修。

### 18.4 修法（四件，同一批）

1. **拱加动画（根因 1，核心）**：Index 新增 `@State archXVp`，初值 `clampedStrikeXVp()`。所有改变拱目标的操作（commitChar／onDelete／onBackLine／onNewline／loadDocument／换纸／换机）之后，统一调 `animateArch()`：`target = clampedStrikeXVp()`，`animateTo({duration: 90, curve: Curve.FastOutSlowIn})` 把 `archXVp` 滑到 target；退行／换行用 200ms（与纸移动同拍）。`CarriageLayers` 三处调用点改传 `archXVp` 不再传 `clampedStrikeXVp()`。**注意：O 本身已有动画，拱再套一层动画会双重平滑——`animateArch` 只跟 target，不跟 O 的中间值；O 的动画继续走，不许为了拱而停掉 O 的动画。**验收标准：任意操作后拱的移动全程连续（逐帧截图无跳变），不是「先跳后滑」。
2. **合并／载入后重算 O（根因 2）**：`onDelete` 里 `backspace()` 返回且行数变了（合并）时，`rewrapOverwideLines` 之后调一次 `recalcOffsetFromCursor()`（用当前光标重算 O 并钳制），再 `syncRows`。`loadDocument` 里 `syncRows` 之后同样调一次。`onBackLine` 已有 targetO，不用再调。修后合并瞬间拱应落在上一行末（模拟值约 460.4，不再是钳住的 524.4）。
3. **钳制不许遮住光标（根因 3）**：`currentLineWidthVp()` 改为只累加到光标 offset 为止（不是整行）。光标恒在行尾时两者相同，合并点光标在行中时拱跟光标走、不跟行末走，行宽一删就变、拱一删就动，不再被整行宽钳住。`clampedStrikeXVp` 的 limit 钳制保留（防拱出纸），但钳制触发时记 hilog `strike clamped raw=… limit=…`（§15 第 3 条已要求，一并落地）。
4. **退行忙窗内禁删（防动画打架）**：`onDelete` 开头加 `if (this.backBusy) return;`（`onBackLine` 的 270ms 窗内删会与它的 250ms O 动画抢 `carriageOffsetVp`）。同时 `onBackLine` 的 setTimeout 释放 `queuedChars` 时，先判 `backBusy` 已清再放行。

### 18.6 忙窗互斥缺口：删／换行／退行不守 backBusy／newlineBusy（2026-11-08 用户让沙箱分析 §18 的附带隐患）

- **机制现状（读码坐实）**：两面旗。`backBusy`（@State，约 133 行）：`onBackLine` 置 true，270ms 后 setTimeout 清 false 并释放 `queuedChars`。`newlineBusy`（约 131 行）：`onNewline` 两处分支置 true，700ms 后（t0 450＋250）setTimeout 清 false 并释放 `queuedChars`。**全仓只有 `commitChar` 一处检查这两面旗**（约 2013 行 `if (this.newlineBusy || this.backBusy)` → 字进 `queuedChars`，不直接落）。打字是守卫的，其余三路全不守。
- **守卫缺口表**：

| 操作 | 检查 busy 吗 | 忙窗内会发生什么 |
|---|---|---|
| 打字 commitChar | 查（进 queuedChars） | 字排队，窗口结束逐字回落字队列，顺序对 |
| 删字 onDelete | **不查** | 立即执行，`stepCarriageRight` 另起一个 `animateTo` 抢 `carriageOffsetVp` |
| 换行 onNewline | **不查** | 立即执行，另起一整套换行编排（置 newlineBusy、排一串 setTimeout） |
| 退行 onBackLine | **不查** | 立即执行，另起一个 250ms O 动画＋270ms 释放 |

- **场景 S1（删 during 退行窗，§18 提示词里点的那个）**：t=0 按退行，O 向 targetO 滑 250ms；t=100ms 按删，`onDelete` 立即跑，`stepCarriageRight` 另起 70ms 弹簧动画抢 `carriageOffsetVp`。ArkTS 里后一个 `animateTo` 会从当前插值接管，前一个动画被打断——O 停在「100ms 时的值＋4.0」，到不了 targetO。270ms 释放时没人再纠正 O，**错位是持久的**（O 再也不从光标重算，见 §18.3 根因 2），拱与纸从此对不上光标。再删只会沿着错的 O 继续拨。
- **场景 S2（删 during 换行窗，700ms，比 S1 更易撞上）**：t=0 按换行，`docModel.newline()` 已跑、光标在新空行行首，编排 600ms＋700ms 释放；t=200ms 按删，`backspace()` 在新行行首 offset 0——**把刚建的新空行又合并回上一行，换行被撤销了**，但纸上滑／字车回位／叮声照常走完。用户看到纸上去了、铃响了，文字却回到了上一行。纸、字车、光标三方失同步。
- **场景 S3（换行 during 退行窗，或退行 during 换行窗）**：两套编排重叠。`onNewline` 的 `resetCarriage`（O 回 0）与 `onBackLine` 的 O 动画（到 targetO）抢同一个 @State；两边的 setTimeout 各自清旗、各自释放 `queuedChars`（先释放的把队清空，后释放的空转）。最终 O 落在哪边取决于哪个动画后完成，与光标不一定一致。
- **场景 S4（连按两次退行，旗提前清）**：t=0 按退行（setTimeout A 定 270ms），t=100ms 再按（setTimeout B 定 370ms，O 向新 targetO 滑到 350ms）。t=270ms A 先到：`backBusy=false`，但 B 的 O 动画还在跑（到 350ms）。**270–350ms 这 80ms 里旗已清、动画未完**，用户打字／删字全放行，直接撞上飞行中的 O 动画。根因：释放没有代际守卫——`newlineTick` 已存在（约 151 行）但只加不查，`backLineTick` 根本没有。
- **场景 S5（打字排队后删，顺序错）**：忙窗内打的字进了 `queuedChars`（未落字）；用户随手按删，`onDelete` 立即删掉了光标前一个**已有的**字；窗口结束排队字才落下。用户本意是「打 X 再删 X」，实际变成「删旧字、再落 X」——删错了字，X 还在。

- **修法（四件，与 §18 前四件同一批）**：
  1. `onDelete`／`onNewline`／`onBackLine` 开头统一加 `if (this.newlineBusy || this.backBusy) return;`（放最前面，`onDelete` 的 §15 落队之前——忙窗内删连落队也不做，队里字照常由释放路径落下，用户窗后再按删）。删／换行／退行是显式按键，忽略后用户可再按，不许排队（排队删会删错字，见 S5）。
  2. 代际守卫：新增 `backLineTick`（@State，`onBackLine` 内 ＋1）；`onBackLine` 的 setTimeout 捕获当时的 tick，只有 tick 没变才清 `backBusy` 并释放 `queuedChars`，变了就什么都不做（让新一轮的 setTimeout 负责）。`onNewline` 同理：释放时比对 `newlineTick`，变了不释放。`newlineTick` 已存在，不用新加。
  3. `onDelete` 开头同时加 `if (this.paperChanging) return;`（与 commitChar 同口径——换纸 600ms 内删会撞上 `DocModelCore.clear()`，同一类缺口，顺手补）。
  4. `commitChar` 里的自动换行调 `onNewline`（约 2031 行）不受影响：`commitChar` 入口已查过 busy，同步代码中间没有别的入口能置旗，调 `onNewline` 时旗必为 false，不会被新守卫误拦。桌面改完须单测／真机确认自动换行仍触发。

### 18.8 候选栏挡住木底板＋按 EN 切换时底板抖、纸被抬高（2026-11-08 用户报，§18 批一并做）

## 十九、手机端布局：零件挤到底板、部分跑出屏幕外（2026-11-08 用户报，附真机截图）

- 用户原话：现在来修一下手机端的布局问题，平板端的代码不要受到影响。主要是零件挤到底板上，而且部分零件跑到外面去了。并且我感觉这个问题可能在其他分辨率的设备上更加严重，我们没办法每种分辨率都试一下实际效果，所以需要你更加聪明的处理来确保显示正确。
- 截图（`screenshot_20261108_163601`，Nova 12 Ultra，1224×2776，vp2px=3.375，屏 362.7×822.5vp）：纸顶约 y=1350px（400vp），纸面区上方约 326vp 全是空暗底；纸可见高仅约 89vp；候选栏（wofe／1 我 2 窝 3 握 4 沃／1/3）压在纸底与字车区上；「1920s／Courier Prime」金牌与键盘挤在一起；左右两端金属件贴到屏幕边。**平板代码一律不动，所有改动只走 `!isTablet` 分支。**
- **根因 1（跑到外面：木底座比手机屏宽，算死）**：`baseW = Pw + 2×knobD`，`knobD = Pw×0.17×0.92`，即 `baseW = Pw×1.3128`。手机 `Pw = 0.82×stageW = 297.4`，`baseW = 390.4vp`，屏宽才 362.7vp——**底座左右各出屏 13.9vp**，滚筒／压纸卷跟着出。平板 `Pw = 0.66×stageW`，`baseW = 583.6 < 673.7`，不出界。所以不是手机「偶然」溢出，是 0.82 这个比例在窄屏上数学上就装不下。
- **根因 2（挤到底板：纸面区没给候选栏留位置＋总成内层 Stack 高用错）**：`measureStage` 算 `region` 时只减顶栏／纸顶空隙／字车／字体条／键区／功能行，**没减候选栏 44vp**（§18.8 只做了常驻占位、没改 region 公式，44vp 仍是白占的）。更深一层：总成内层 Stack 高是 `availableHeightVp`（整窗可用高，手机约 777vp，约 2904 行），而它外面 `layoutWeight(1)` 的容器只有 `region` 高（手机约 412vp）——**内层比容器高出约 365vp，`clip(false)` 任其溢出**，纸／字车／底座按大 Stack 定位，实际落点比布局低一截，正好压到候选栏／字体条／键盘上。平板同一结构没报，是比例恰好遮住了，不是它对。
- **根因 3（比例不随分辨率走）**：`carriageTopVp = 0.56×H`、`Pw = 0.82×stageW` 都是按一台设备调死的比例。手机屏比平板高得多（822.5vp vs 673.7vp 有效高），0.56 一乘，纸顶到顶栏之间空出 326vp 暗底；换一台更窄／更矮的屏，溢出只会更严重。**不能每种分辨率试一遍，必须改成按约束算：每个尺寸都由「装得下」反推，而不是由固定比例正推。**

### 19.1 修法（只改手机分支，平板一律不动；全部按约束算，不写死新比例）

1. **纸宽按「底座装得下」反推（根因 1，手机分支）**：`measureStage` 里 `paperWidthVp` 定稿后、仅 `!isTablet` 时加一道钳制——`Pw ≤ (stageW − 2×margin) / 1.3128`，`margin = 8vp`（底座离屏边各 8vp，不许贴边）。手机 stageW=362.7 时 `Pw ≤ 264.1vp`（现 297.4，需收窄）。**系数 1.3128 不许写死**，写成 `(1 + 2 * 0.17 * 0.92)`（即 `1 + 2×Hc系数×旋钮系数`），与 `CarriageLayers` 的 `baseW()`／`knobD()` 同源，改一处即同步。收窄后 `Hc／knobD／carriageHeight／maxTravel／travelPerChar／每行字数` 全由 `recalcTravel()`／`recalcPaperHeight()` 按新 Pw 重算，不许另写一套。代价：每行字数少 2–3 字（纸窄了），换「全部零件不出屏」，值。
2. **`region` 减去候选栏（根因 2，手机分支）**：`measureStage` 算 `region` 时，仅 `!isTablet` 再减 `CANDIDATE_BAR_HEIGHT_VP`（44vp，与 `CandidateBar.ets` 的 `.height(44)` 同源，最好抽成常量共用，不许两处各写 44）。平板 `region` 公式不动。
3. **手机总成内层 Stack 高与字车位置改按 `region` 算（根因 2，深层，手机分支）**：约 2904 行内层 Stack 的 `.height(...)` 改为 `this.isTablet ? this.availableHeightVp : this.regionHeightVp`；`recalcPaperHeight` 里 `H` 的取值改为 `this.isTablet ? ### 19.1 手机跟进：纸与纸筒断开、右侧拨杆出屏（2026-11-08 用户报，附真机截图）

- 用户原话：手机端的纸张出现问题，移动时和纸筒是断开的，并且右侧的拨杆也显示到了屏幕外。截图（`screenshot_20261108_171716`，已打 `9你好你好你好` 一行，O≈−26.5）：纸右缘约 255–281vp、滚筒右缘约 299vp，纸相对滚筒左移；拨杆（右上角弯曲金属杆）尖端出屏。
- **拨杆出屏（根因算死）**：支点 `pinXRel ≈ 314.9vp`（支架销钉孔，离屏右缘只 47.8vp），杆长 `leverH = Hc×2.5 = 112vp`，静止外倾 30°、摆到 65°。尖端横向伸出 `leverH×sinθ`：静止 `112×sin30° = 56vp` → 尖端 371vp，出屏 8vp；摆满 `112×sin65° = 101vp` → 尖端 416vp，出屏 54vp。平板屏宽 673.7vp 够，手机 362.7vp 不够。**不是偶然，是杆太长＋角度太大＋支点太靠右，三者叠加。**

### 19.2 修法（只改手机分支，平板一律不动）

1. **拨杆：手机上按「尖端不出屏」反推杆长与角度（根因 1）**：先算可用横向空间 `leverReachMax = stageW − 8 − pinXRel()`（手机约 39.8vp）。手机分支同时做两件——① 杆长封顶：`leverH = min(Hc×2.5, leverReachMax / sin(最大摆角))`；② 角度收小：静止角与摆幅改由 `LeverLayer` 的 props 传入（现 `REST_DEG=30／SWING_DEG=35` 是写死常量，须改成可传参），手机取静止 15°、摆幅 20°（最大 35°）。代入：杆长取 `min(112, 39.8/sin35°=69.3) = 69.3vp`；静止尖端 `314.9+69.3×sin15° = 332.8vp`、摆满 `314.9+69.3×sin35° = 354.5vp`，均在屏内（限 354.7vp）。代价：手机拨杆比平板短、摆幅小、尖端够不到纸顶——这是窄屏的必然取舍，不许为了「够到纸顶」把尖端再推出屏。平板 `REST_DEG／SWING_DEG／leverH` 全不动。
2. **纸与纸筒：手机上恢复同步（根因 2）**：手机分支 `ROLLER_K` 改回 **1.0**（滚筒走满 O，与纸永远对齐，分离恒为 0）。§18.7 的「滚筒不出底座」改由限行程兜底：手机分支 `maxTravelVp` 再加一道封顶——滚筒左缘在满行程时不许出屏，即 `maxTravel ≤ paperLeftFixed − (rollW−Pw)/2`（手机约 42.8vp；`paperLeftFixed=(stageW−Pw)/2`，`(rollW−Pw)/2≈6.6vp`）。于是 `maxTravelVp = min(64, Pw×0.25, paperLeftFixed − (rollW−Pw)/2)`，手机取约 42.8vp。代价：手机每行字数从 16 字降到约 10 字（中文 4.0vp／字）、英文从 26 字降到约 17 字；行满自动换行提前触发。**取舍已定**：宁要行短一点，也不要纸滚筒断开、不要滚筒出屏。行末滚筒左缘可能比底座左缘再出约 8vp（滚筒是活动件、随字车走，8vp 内可接受，不许再为此把 K 调回去）。
3. **不许做的**：不许只把拨杆 `clip` 在屏边（尖端被切断更难看）；不许把 `ROLLER_K` 调回 0.8 附近「折中」（分离只是变小、不断根）；不许动平板的 `ROLLER_K=0.8／maxTravel=64／拨杆角度`。

## 十八点十、换纸时哥特拱不归位（2026-11-08 用户报）

- 用户原话：换纸的时候是不是有 bug，我发现换纸时哥特扣没有正确归位（要正确带有动画）。
- **根因（读码坐实）**：`onPaperChange()`（约 2319 行）第②步做了 `docModel.clear()`＋`syncRows()`＋`carriageOffsetVp = 0`，但**全程没有调用 `animateArch()`**。拱的实际位置 `archXVp`（@State，唯一渲染源）只由 `animateArch()` 改写；换纸不调它，拱就停在换纸前的位置（例如打满一行后的行末，约 460vp），不回行首。对比：`loadDocument()`（约 2595 行，同样是「文档清空重来」）就同时调了 `recalcOffsetFromCursor()`＋`animateArch(90)`——换纸漏了后者，就是 bug。

### 18.7 纸筒（滚筒）中文输入时跑出木底座：滚筒移动须单独调速（2026-11-08 用户报，§18 批一并做）

- 用户原话：在输入中文内容时，纸筒组件可能会跑到整个木底座的外面，需要单独调整下它在这种情况下的移动速度。
- **所指组件**：代码里没有「纸筒」这个名字；用户说的就是 `CarriageLayers.ets` 的滚筒（`part === 'roller'`，`roller-texture-v7.jpg` 的圆柱体，纸裹在它上面成筒状）。木底座是 `part` 里的底座件（`baseW()`／`baseLeft()`）。
- **几何（读码＋数值模拟坐实）**：
  - 木底座**不动**：`baseLeft() = paperLeftFixedVp − knobD`，用固定左缘（不含 O），`baseW = Pw + 2×knobD`。平板：底座左 45.0、右 628.7；手机：底座左 −13.9、右 376.6。
  - 滚筒**跟 O 走**：`rollX() = paperLeftVp − (rollW−Pw)/2`，`paperLeftVp = paperLeftFixedVp + carriageOffsetVp`，`rollW = Pw/0.9528`。O 从 0 到 −64（maxTravel），滚筒跟着左移 64vp。
  - **出界量**：O=−64 时，平板滚筒左缘 39.5，底座左缘 45.0——**滚筒左出底座 5.5vp**；手机滚筒左缘 −38.7，底座左缘 −13.9——**左出 24.9vp，且左缘已出屏幕（x<0）**。O=0 时两端都在底座内。右缘从不出界。
  - **为什么中文才明显**：中文 travelPerChar 4.0vp／字（§15 后分语言），英文 2.46vp／字——**中文每字滚筒快 1.63 倍**；4 字词连落中文滚筒走 16vp、英文 9.8vp；中文 16 字即打满一行到顶（O=−64），英文要 26 字。中文步子大、成词连落成串、更快到顶，滚筒「跑出去」在中文下最显眼。
- **修法（滚筒单独调速＋钳制兜底）**：
  1. `CarriageLayers` 新增 `@Prop rollerOffsetVp`（滚筒横向偏移，默认等于 `carriageOffsetVp`）。Index 三处调用点传 `rollerOffsetVp = this.carriageOffsetVp * ROLLER_K`，`ROLLER_K` 为常量（初值 0.8）。`rollX()` 改用 `paperLeftFixedVp + rollerOffsetVp − (rollW−Pw)/2`，不再直接用 `paperLeftVp`。**纸张、压纸卷、中央件继续用满 O，不动**——只调滚筒，不动纸。
  2. 系数要按几何算，不许拍脑袋：滚筒左缘不出底座的条件是 `k ≤ (knobD − (rollW−Pw)/2) / maxTravel`。平板上限 0.914，手机上限 0.612。**固定 k=0.8 只保平板（余 7.3vp），手机仍出 12.1vp。**所以再加一道钳制兜底：`rollX()` 返回前钳住，`rollX = max(rollX, baseLeft())`（左缘不许左出底座左缘），右缘不管（从不出界）。系数＋钳制双保险，两台设备都守住。
  3. 注意纸筒错位 trade-off：滚筒走 `k×O`、纸走满 O，O=−64 时纸比滚筒多左移 `(1−k)×64`（k=0.8 时 12.8vp）。纸底在滚筒处被 clip 截断，错位藏在卷曲阴影下，视觉上可接受；桌面须截图确认纸底与滚筒接缝处无穿帮（纸悬空露在滚筒外、或纸被滚筒盖住半截都算失败）。若错位肉眼可见，把 k 往上调（0.85／0.9）并靠钳制兜底，不许把纸也改慢。
  4. 动画口径：`rollerOffsetVp` 是 @Prop，随 `carriageOffsetVp` 的 `animateTo` 一起变，不另起动画（另起动画会让滚筒与纸错拍）。滚筒「慢」靠系数 k（步子小），不是靠拉长动画时间。
- **验收（识屏）**：
  - 中文打满一行（16 字）到顶：截图确认滚筒左缘在底座左缘之内（平板余量 ≥0，手机余量 ≥0），滚筒没有一半悬在底座外、没有出屏幕左缘；纸底与滚筒接缝无穿帮。
  - 中文连打一个 4 字词：逐字截图（或录屏抽帧），滚筒每字移动约 `4.0×k` vp（k=0.8 时约 3.2vp／字），全程平滑、无跳变、无一帧出底座。
