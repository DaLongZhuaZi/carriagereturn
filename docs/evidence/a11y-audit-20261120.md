## 一、权威口径（设计要求汇总）

### 1. 用户 2026-11-13 定夺（canvas-resolve.md R-S12）

> 无障碍默认不降级，逐键读屏以透明原生按钮覆盖层全量补。

- §5.1 无障碍行（R-S12 修法后）：“全量可交互元素均须有无障碍节点（**透明原生按钮覆盖层全量覆盖，或对应原生组件保留**）”。
- 全量清单：四机全部键帽（1920s 43／1930s 58／1950s 49／1960s 52，另有空格条）＋功能行六键＋TopBar 三图标＋候选栏 chip；按钮位置随变换矩阵同步（与 R-S6 同一份定义）。
- Q3 改为实现形式之问：覆盖层分几批做？（缺省：Phase 2 一次全量；备选：先补功能行＋TopBar、键帽后补——分批不降级，只是排期）。
- §9：覆盖层做不到全量时，回报用户定夺覆盖范围分几批做，不降级口径不变。

### 2. P5 读屏判定项（R-S20）

> P5 的判定项为“两路截图入画＋读屏逐键可达”——读屏扫一遍，抽测不少于 10 帽＋功能行六键逐键可达且朗读文本正确；达不到即 P5 不通过，不得以“如实记录”放行。

### 3. canvas-invest-api.md §7.1（无障碍／读屏）

- 结论：有条件——Canvas 整页只有一个无障碍节点；逐键读屏须另做覆盖层。未查到官方说法。
- 机理：Canvas 内容是位图式绘制，不生成无障碍节点；读屏只能识别到 Canvas 组件本身（可挂 `accessibilityText` 等通用属性做整体描述）。
- 缓解：给 Canvas 挂整体无障碍描述；如需逐键读屏，须在 Canvas 上叠加一层透明原生按钮（仅作无障碍节点，不参与视觉），或保留关键按钮为原生组件。
- **须真机用读屏验证。**

### 4. 适用范围说明（重要前提）

R-S12 是 **Canvas 方案（打字机主屏进 Canvas）**下的要求。当前 App 仍是 ArkUI（未进 Canvas），所以“覆盖层”的前提（Canvas 不生成无障碍节点）在现行 App 下并不成立——现行键帽本身就是原生 `Button`，已有无障碍节点。R-S12 的“**或对应原生组件保留**”这一半，恰好覆盖现行 ArkUI 的情况。因此：桌面端在批 62 收尾改用原生 Button 的 `accessibilityText`（不另铺覆盖层），在 R-S12 字面上是合规的机制选择；审计的重点是该机制之外的要求（开关控制、文本正确性、验证、其他页面）是否落实。

### 5. 触摸目标口径：设计稿里没有有效的最小值

- 44vp 曾在 24 号稿 v1 提出（“帽高 ≥44vp”），后在 v2.1 被**删除**（24-review-structural.md M3：参数全空、补救措施“减列数”不存在；**44vp 本身无来源**，未引任何平台无障碍／人机界面规范）。
- 48vp 在设计稿里**从未定过**（唯一一次出现是评审里的假设句：“若平台下限实际是 48vp……”）。
- 现行口径（24 号稿 v2.1 §3.5）：键帽实测帽面 21.0×18.7vp（PIL 连通域量测），**触摸目标按帽心间距计**。设计稿无有效的最小触摸目标数值线。

## 三、打字页可交互元素逐项核对

### 3.1 四机键帽：有节点，但文本有两处错、计数口径与代码不符

- **已落实的部分**：`KeyGrid.ets:391-393`，每个键帽 `Button` 上加了三行（`ForEach` 全帽共用，一处代码覆盖全部帽子）：
  ```ts
  .accessibilityText(p.legend.length > 0 ? p.legend : p.label)
  .accessibilityLevel('yes')
  .accessibilityDescription(p.sub.length > 0 ? p.sub : p.label)
  ```
  字母键读大写字母（如 'Q'），与帽面显示一致。
- **错误 1——数字行 10 键读成移位符号**：`K()` 签名是 `K(label, legend, sub, w, kind, up, alt)`（`KeyGrid.ets` 约 30 行），数字键定义为 `K('1', '!', '1', 21.6, ...)`（`KeyGrid.ets:138-142`）——label 是数字 '1'，legend 是移位符号 '!'。帽面双行显示：legend '!' 在上、sub '1' 在下。但 `accessibilityText` 取的是 legend，所以 '1' 键读作“!”、'2' 读作“@”、'3' 读作“#”……10 个数字键（1–0）全部读成 `! @ # $ % ^ & * ( )`，而非数字本身。主键是不加 Shift 落下的数字，读移位符号是错的。
- **错误 2——空格条读成空白**：空格键定义 `K(' ', '', '', 237, 'space', '', '')`（`KeyGrid.ets:122/175`），label 是单个空格、legend 为空。`accessibilityText` 回落到 label，即单个空格 `' '`——读屏基本读不出内容。应读“空格”。
- **语言不一致（无口径）**：特殊键读英文——Tab 读 'TAB'、Caps Lock 读 'SHIFT LOCK'、Return 读 'RETURN'、Backspace 读 'BACK SPACE'、Shift 读 'SHIFT'；而功能行 BL 读中文“退行”。设计稿没有规定特殊键名的语言口径，中英文混用是事实。
- **计数口径与代码不符**：R-S12 清单的 43／58／49／52 是四机 keymap JSON 的历史帽数（实测 JSON：1920s 43、1930s 58、1950s 49、1960s 52，与清单一致）。但当前 `KeyGrid.rows()` 是**写死的单一布局**（`KeyGrid.ets:130-190`，字母模式 54 帽：数字行 13＋Q 行 13＋A 行 15＋Z 行 12＋空格 1；符号模式 53 帽），`layout` prop 是死的——`this.layout` 在 `KeyGrid.ets` 全文**零引用**，`displayLayout()` 传进来的四机布局没人用。四机共用同一套键位。清单的按机型计数描述的是 keymap JSON，不是现行键盘。现行键盘的全部 54 帽都有文本（覆盖 live 布局是全的），但“四机各多少帽”的清单口径在代码里不存在。

### 3.2 TopBar：现存 2 键都有文本；清单的“第三图标”元素不存在

- **已落实**：`TopZone26`（`Parts26.ets:186-262`）现存的 2 个可点击元素都有文本——返回拨杆 `Parts26.ets:219-220`（'返回'，16×32vp）、出纸槽 `Parts26.ets:236-237`（'出纸槽'，50×12vp）。
- **缺的不是文本，是元素本身**：`TopZone26` 声明了 `onBell`（`Parts26.ets:197`）与 `onPlate`（`:199`）两个回调，`Index.ets:4997-5010` 挂载时也传了 `onBell: toggleSound` 与 `onPlate: onPlateTap`，但 `TopZone26.build()` 里**根本没有渲染边铃与铭牌元素**——两个回调声明了、传了、没人调用。顶区注释（`Parts26.ets:182`）还写着“黄铜铭牌／返回拨杆／边铃／出纸槽／库与菜单”，实际只剩返回与出纸槽。旧 `TopBar.ets`（69 行，内有 3 个 onClick）是死代码：`Index.ets:74` import 了它，但全文无 `TopBar(` 实例化。
- 结论：按**现行 UI** TopBar 覆盖是 2/2；按 R-S12 清单的“TopBar 三图标”是 2/3——缺的那一个不是没加文本，是整个可交互元素不存在。

### 3.3 功能行、候选栏、字体条、出纸槽

- **功能行六键——已落实**：`Parts26.ets:442-443`，`cap()` 根 Stack 加 `.accessibilityText(label === 'BL' ? '退行' : label)`＋`.accessibilityLevel('yes')`。六键（中/EN、⌫、⏎、↻、BL、Aa）都有文本，BL 读作“退行”正确。
- **候选栏 chip——已落实**：`Parts26.ets:540-541`，`CandStrip26` 的 `Text(c)` 加 `.accessibilityText(c)`＋`.accessibilityLevel('yes')`，读候选词本身，与格内显示一致。
- **字体条——部分落实**：`Parts26.ets:490-491`，`FontPlate26` 整 Stack（346.7×28vp）加 `.accessibilityText('字体')`＋`.accessibilityLevel('yes')`。但文本是通用词“字体”，不传达当前字体名——条上显示的是具体字体名（如 `label` prop 的 'Courier Prime'），读屏用户听不到当前是哪款字体。
- **出纸槽——已落实**：见 §3.2。

### 3.4 打字页其他可交互元素

- **悬浮 'A' 按钮——未落实**：`Index.ets:5390-5396`，`Text('A')` 44×44（`.position({ x: stageWidth - 56, y: topInset + topBarHeight + 16 })`），`.onClick(() => { langZh = false; applyChineseMode(false); })`，**无 accessibilityText**。读屏只能读到字母“A”，不知道它是“切换到英文”。`Index.ets` 全文零 accessibility* 属性，这是其中一个实例。

## 四、无障碍开关（a11yOverlayEnabled）到底控制了什么

**结论：除了翻转 state、同步开关显示之外，什么都不控制。**

全仓引用只有 4 处（代码 2 文件＋文档）：

| 位置 | 内容 | 作用 |
|---|---|---|
| `Index.ets:992` | `@State a11yOverlayEnabled: boolean = false;` | 声明，**初值 false（默认关）** |
| `Index.ets:5179-5180` | `a11yEnabled: this.a11yOverlayEnabled` / `onToggleA11y: () => { this.a11yOverlayEnabled = !this.a11yOverlayEnabled; }` | 传给设置页、翻转 state |
| `SettingsPage.ets:55` | `@Prop a11yEnabled: boolean = false;` | 接收（批 62 改成 @Prop，显示会同步） |
| `SettingsPage.ets:174` | `switchOn: this.a11yEnabled` | 开关显示 |

- **没有任何渲染或无障碍节点读它**：批 62 收尾加的 13 行 accessibility 属性全是**无条件**加的（`KeyGrid.ets:391-393`、`Parts26.ets:219/236/442/490/540` 均无 `if (a11yOverlayEnabled)` 守卫）。开关拨动不增减任何节点、不改变任何行为。
- **开关的归类还是 Canvas 调试遗留**：`SettingsPage.ets:167` 注释原文——“2b Canvas 调试（2B-8 回滚 / 2C-2 无障碍覆盖层）”，开关标签是“无障碍覆盖层”（`:172`）。它从来不是产品级无障碍设置，是 Canvas 时期的调试开关。
- 因此：用户 2026-11-20 六问③里“设置真的生效吗”的问题，对这个开关而言答案仍是**不生效**——显示修好了（@Prop），行为还是死的。

## 六、触摸目标尺寸（手机，sx=sy≈1.0）

`KeyGrid` 挂载参数（`Index.ets:5122-5131`）：`sx: this.xk(), sy: this.yk()`，手机档 xk=yk≈1.0。实测尺寸如下（可点区域＝带 onClick 的组件盒）：

| 元素 | 可点尺寸（vp，手机） | 说明 |
|---|---|---|
| 键帽（字母行） | 宽 17.25–22.4 × 高 27.6 | `KB_CAP_H=27.6`（`KeyGrid.ets:26`）；Q 行 22.4、A 行 17.25、Z 行 21.17；横缝 3（`KB_HGAP`）、行高 34.5（`KB_ROW_H`） |
| 键帽（特殊键） | Tab 33.6、Caps Lock 31、Return 41.4、Shift 47、Backspace 43.2、空格 237 × 高 27.6 | 同上 |
| 功能行单键 | 36 × 30 | `Parts26.ets` `cap()`：`.width(36*sx).height(30*sy)` |
| TopBar 返回 | 16 × 32 | `Parts26.ets` 返回 Stack：宽仅 16vp |
| 出纸槽 | 50 × 12 | `Parts26.ets` 出纸槽 Stack：高仅 12vp |
| 字体条 | 346.7 × 28（整 Stack 可点） | 可见铜牌 240×20，但 onClick 在外层 Stack |
| 候选 chip | 约 16–32 宽 × 约 20 高（随词长） | `Text(c)` 本身可点（16vp 字号），Row 300×30 不可点 |
| 悬浮 'A' | 44 × 44 | `Index.ets:5390-5396` |

**判定**：设计稿无有效最小值口径（44vp 已删、48vp 未定，见 §1.5），所以无法以“低于 44/48vp 即不达标”判定。仅记录事实：返回键宽 16vp、出纸槽高 12vp、候选 chip 高约 20vp、A 行字母键宽 17.25vp，都是偏小的；键帽 Button（17.25–22.4×27.6）略大于 24 号稿实测的可视帽面（21.0×18.7vp），与“触摸目标按帽心间距计”的口径一致（帽心横间距＝键宽＋3vp 横缝，约 20–25vp；行间 34.5vp）。

## 七、纸面内容读屏：未显式落实

- `PaperPanel26`（`Parts26.ets:557-677）全文**零 accessibility\* 属性**；每行文字 `Text(line.length > 0 ? line : ' ')`（`:642`）无 `accessibilityText`/`accessibilityLevel`；`PaperPanel26` 挂载处（`Carriage26.ets`）与 `Index.ets` 纸面挂载处也无。

- 结论：**未显式落实**，仅靠默认行为，状态未验证。

## 十、总判断

**无障碍作为底层设计，落实了约三成。** 打字页核心元素的“有没有无障碍文本”这一层基本有了（13 行显式属性，键帽、功能行、TopBar 现存两键、候选 chip、字体条、出纸槽全覆盖），且机制上走了 R-S12 允许的“原生组件保留”分支；但缺的最关键的三件是：**① 无障碍开关是死的**（`a11yOverlayEnabled` 初值 false，全仓仅 4 处引用，无一控制行为，且开关本身归类还是“Canvas 调试”遗留）；**② 读屏验证一次没做过**（P5 判定项要求的抽测 10 帽＋功能行六键逐键可达且朗读文本正确，无人验过）；**③ 文本内容有错**（数字行 10 键读成移位符号、空格条读成空白、字体条不报当前字体名、特殊键中英文混用）。其余缺的：焦点顺序、纸面读屏设计、其他页面显式无障碍、触摸目标口径——设计稿本身也没有这些口径，代码里自然也没有。
